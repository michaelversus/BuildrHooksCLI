# Account usage monitoring design

Status: design confirmed by the user on 2026-10-11; discussion complete. Published as [specification #20](https://github.com/michaelversus/BuildrHooksCLI/issues/20), labelled `ready-for-agent`. These are agreed requirements, not implemented behavior.

## Agreed decisions

- Deliver Codex first, with other providers, including Claude, supported by the design. Monitor the currently authenticated Codex account only.
- Require explicit provider selection. Adding a provider does not expand an existing installation's collection scope automatically.
- Use an explicitly enabled CLI-managed login service. Enabling starts collection immediately and at future logins; disabling stops collection immediately and removes automatic startup.
- Closing BuildrAI windows keeps monitoring active. Quit/Command-Q fully exits BuildrAI; the independently enabled collector continues running.
- Poll every five minutes, fetch immediately at collector startup and after wake, and publish every successful fresh fetch even when values are unchanged. Provider throttling can extend the interval.
- Send minimal usage snapshots directly through distributed notifications. Exclude credentials, identifying details, filesystem paths, and raw provider responses/errors. Receivers treat messages as untrusted display data.
- Use `ai.buildrai.account-usage-updated`, `ai.buildrai.account-usage-status-updated`, and `ai.buildrai.account-usage-requested`. Snapshots and status use bounded JSON in the `payload` userInfo key with schema version 1. Requests carry no payload and request all available providers.
- Separate collection status from observed usage. Distinguish authentication required, temporary failure, and throttling; preserve the last successful values and collection time on failure. A successful fresh fetch clears failure status.
- Mark snapshots stale at fifteen minutes while retaining values and original collection time. Known authentication failure is surfaced immediately.
- Persist minimal snapshots atomically at `~/.codex/buildr-artifacts/account-usage.json`. Retain the cache across collector restarts and disabling; provide an explicit clear operation.
- At BuildrAI startup, request immediate recovery. Replay both the cached snapshot and latest collection status with their original timestamps; replay never makes an observation fresh.
- Verify account continuity before replaying persisted usage. If identity is unavailable, fetch fresh usage before delivering a snapshot and report collection pending meanwhile. Discard previous-account usage on a detected account change and instruct BuildrAI to clear it; keep comparison identity private to the collector.
- Include all available limit buckets and windows, preserving actual durations and reset times. Missing duration remains unknown. Defer all credits from schema version 1.
- Use Codex account and limits events to trigger coalesced, throttled full fetches alongside polling. Partial events are not complete snapshots.
- An explicit clear discards cached and in-memory usage and requests clearing retained usage in running BuildrAI. Collection continues and the next successful fetch may populate usage again. A fully quit BuildrAI reconciles clearing at its next startup.
- Persist a locally salted account fingerprint in collector-owned metadata to verify continuity after restarts. Store no raw account ID or email, and exclude fingerprints from notifications and logs. Insufficient identity requires a fresh fetch before usage delivery.
- Use durable per-provider ordering and an invalidation marker in collection status. Recovery includes invalidation even when no snapshot remains. Earlier snapshots cannot restore usage after clear or account change; snapshot and status freshness remain separate.
- Bound each fetch to thirty seconds. Retry temporary failures with exponential delays starting at thirty seconds and capped at five minutes, with jitter; honor longer provider retry delays. Authentication failures wait for an authentication event or the next scheduled check. Recovery requests do not bypass throttling.
- Report `usage_unavailable` when authenticated collection supplies no usable subscription limits. Retain earlier observations only with verified account continuity. Missing windows remain absent; an empty successful response does not refresh the last usage snapshot.
- Expose `usage refresh --provider codex`, `usage watch --provider codex`, `usage service enable --provider codex`, `usage service disable`, `usage service status`, and `usage clear --provider codex`. Provider selection is repeatable for future support. Support `--json` command results; service status reports enabled providers, process health, and collection status without identifying account details.
- Allow one collector per macOS user, owning a persistent Codex app-server connection and restarting that connection after failure. A conflicting foreground watch exits with a diagnostic. One-shot refresh uses private local IPC to request collection from a running collector; otherwise it acquires the same exclusive ownership for its fetch.
- Encode timestamps as Unix milliseconds and cap encoded payloads at 64 KiB. Reject unsupported versions, malformed fields, non-finite or negative percentages, invalid durations, timestamps more than two minutes ahead, and superseded messages. Unknown duration/reset stays absent; percentages above 100 are valid. Old snapshots remain acceptable for recovery and display as stale.
- This repository owns the collector, service, sender, and documented shared contract. BuildrAI separately owns the receiver, widget storage, background setting, and display. Validate each side's contract independently, with a separate end-to-end integration check. An injected notifier does not prove macOS delivery; no additional runtime probe is required during this discussion.
- Snapshot fields are schema version, provider, durable revision, collection time, and windows containing a non-account-specific limit code, window role, percentage used, optional duration, and optional reset time. Status fields are schema version, provider, durable revision, observation time, status code, optional retry time, and latest invalidation revision. Replays preserve revisions/timestamps; snapshot and status ordering are separate. Window roles never imply durations. Status codes are `pending`, `ready`, `authentication_required`, `temporary_failure`, `throttled`, and `usage_unavailable`.
- Use an owner-only Unix-domain socket beside the existing cache for private refresh/clear requests, with bounded requests, peer ownership checks, and an exclusive collector lock. Distributed notifications handle snapshot/status delivery and recovery requests.
- Enabling installs a user-level LaunchAgent that directly runs the CLI using explicit executable paths. Validate CLI/Codex paths first, preserve stable paths across upgrades, and offer a Codex-path override. Missing executables fail with actionable diagnostics; never install Codex automatically. Re-running enable updates configuration. Disable stops/removes the LaunchAgent and retains cache metadata.
- `usage refresh` waits for a fresh collection result. Success requires fresh collection and an attempted publication, not acknowledged receipt. Throttling, authentication, timeout, and unavailable usage produce distinct machine-readable outcomes and nonzero exit codes.
- Clear persists an invalidation marker and attempts immediate delivery without launching an application. When BuildrAI is quit and the collector is disabled, reconciliation waits for their next available recovery exchange. Commands distinguish local clearing and attempted publication from confirmed widget clearing; notification delivery is not acknowledged.
- Coalesce full-fetch triggers with at least thirty seconds between fetch starts per provider, honoring longer retry restrictions. Replay recovery state at most once per second globally without triggering a fetch. Explicit refresh follows the same restrictions and reports a retry time when throttled.
- Automatically restart an enabled collector after crashes with backoff to avoid rapid crash loops. Disable cancels collection, closes the Codex connection, and waits up to five seconds before terminating only owned processes. Preserve committed cache state and never publish incomplete fetches.

## Validation and integration

CLI acceptance requires meaningful tests for normalization, credential exclusion, validation bounds, revision/invalidation ordering, account verification, independent provider state, replay, throttling, cancellation, single-instance ownership, and command outcomes. Use injected clocks/transports, temporary storage, and simulated providers rather than live credentials.

Preserve existing hook behavior. Update help, capabilities, and documentation for the new commands and protocol. Actual notification delivery and widget behavior require a later BuildrAI integration check; no new runtime probe is part of this discussion.

The two-minute future-timestamp restriction applies to collection and status observation times. Reset and retry times may legitimately be in the future. Delayed snapshots are accepted only when their revision remains valid, and remain stale according to their original collection time.
